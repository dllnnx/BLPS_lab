# RBAC, CIDR и сетевые политики — конспект и что сделано в проекте

Документ объединяет **теорию** (что такое RBAC, CIDR, зачем политики по IP, JWT и заголовки) и **описание реализации** в модуле `ozon-service`.

---

## 1. RBAC (Role-Based Access Control)

**Идея:** доступ к операциям не привязывают напрямую к пользователю, а через **роли**. Роли содержат **привилегии** (permissions / authorities). Пользователю назначают одну или несколько ролей.

- **Пользователь** → **роли** → **привилегии** → проверки в коде (`@PreAuthorize("hasAuthority('...')")` и т.п.).
- Плюсы: проще менять права для группы пользователей, меньше дублирования, понятная модель для аудита.

В проекте привилегии заданы в `RolePrivilegeRegistry` (например `ORDER_CREATE`, `ORDER_VIEW_ALL`). Роли из БД: `USER`, `PICKUP_POINT_ADMIN`, `ADMIN`.

---

## 2. CIDR (IPv4)

**CIDR** (Classless Inter-Domain Routing) — запись **адрес сети / длина префикса**, например `192.168.0.0/24`.

- Число после `/` — **длина префикса** (сколько старших бит фиксированы под сеть). Чем **больше** это число, тем **уже** подсеть и тем **конкретнее** правило.
- Примеры:
  - `0.0.0.0/0` — весь IPv4 (префикс **0**).
  - `173.0.0.0/8` — все адреса `173.*.*.*` (префикс **8**).
  - `173.0.0.0/24` — только `173.0.0.*` (префикс **24**).

Проверка «попадает ли IP в сеть» делается через маску; в Spring удобно использовать `IpAddressMatcher` из Spring Security.

## 3. Сетевые политики в задании

**Сущность политики** (в терминах ТЗ):

- `name` (обязательно, до 100 символов),
- `description` (опционально),
- `addresses[]`: список `{ addr: CIDR, description? }`,
- к политике привязан набор **имён ролей**, для которых она действует.

**Логика (как в ТЗ):**

1. У пользователя в БД есть **назначенные роли** (например A, B, V).
2. Учитываются только политики, у которых пересечение **ролей политики** с **ролями пользователя** непустое.
3. Если **ни одна** роль пользователя не фигурирует ни в одной политике — **эффективных ролей нет** (доступ как «пустой»).
4. Для каждой подходящей политики смотрим все её CIDR; если IP клиента попадает хотя бы в один CIDR, политика **матчится**; для политики берётся **максимальная среди совпавших CIDR длина префикса** (самая «узкая» сеть).
5. Среди всех матчнувшихся политик выбираем **максимальную длину префикса** глобально. Все политики с этой длиной считаются **победителями** (при равенстве маски — объединяем роли).
6. **Эффективные роли** = **пересечение** ролей пользователя с **объединением** ролей, указанных у победивших политик.

Примеры из формулировки задания:

- IP `173.0.0.5` попадает в `/0`, `/8`, `/24` → побеждает **/24** → остаётся роль **A** (если только она на политике `/24`).
- IP `173.12.34.56` попадает в `/0` и `/8`, не в `/24` → побеждает **/8** → роли **A и B**.

Реализация: сервис `NetworkPolicyAccessService`, логирование эффективных ролей на **INFO**.

## 4. JWT и привязка к IP

**JWT** (JSON Web Token) — подписанный токен с утверждениями (claims). Сервер проверяет подпись и срок действия; состояние сессии на сервере не обязательно.

**Что сделано:**

- При **логине** (`POST /api/auth/login`) после проверки пароля вычисляются **эффективные роли** по IP, из них — **привилегии**, в JWT кладутся: `sub` (логин), `ip` (IP на момент входа), `priv` (список привилегий), опционально `pp` (pickup point id).
- На каждом запросе фильтр `JwtAuthenticationFilter` снова вычисляет **текущий клиентский IP** и сравнивает с `ip` в токене. **Несовпадение → 401** (токен для этого запроса недействителен).

Так выполняется требование **инвалидации при смене IP** без хранения чёрного списка токенов на сервере (чисто за счёт claim + проверки).

**Алгоритм подписи:** HS256, секрет `app.jwt.secret` (не короче 32 байт), время жизни `app.jwt.expiration-ms`.

## 5. Откуда берётся IP и подмена через заголовки

Класс **`ClientIpResolver`**:

1. Если `app.security.use-client-ip-header=true`, читается заголовок `app.security.client-ip-header` (по умолчанию **`X-Client-IP`**). Первое значение, если через запятую передано несколько.
2. Иначе **`X-Forwarded-For`** (первый hop).
3. Иначе **`request.getRemoteAddr()`**.

Так можно **эмулировать** другой IP в тестах (Docker, curl): передать `X-Client-IP: 173.0.0.5`.

### Как защититься от подделки IP через заголовки (словесно, без обязательной реализации)

Заголовки вроде `X-Forwarded-For` и кастомных `X-Client-IP` **клиент может подставить сам**, если запрос идёт напрямую в приложение. Ими нельзя слепо доверять.

Типичная защита:

1. **Доверять только прокси, которым вы управляете.** Схема: клиент → **reverse proxy** (nginx, Envoy, ingress) → приложение. Прокси **удаляет** входящие `X-Forwarded-For` от клиента и **сам** выставляет доверенный список или один IP.
2. **Список доверенных прокси** (trusted proxies): брать `X-Forwarded-For` / `X-Real-IP` только если `remoteAddr` принадлежит известному прокси; иначе игнорировать заголовки.
3. В **кластере Kubernetes** часто используют контроллер ingress, который нормализует заголовки; приложение настраивают знать «один hop».
4. Для **отладки** отдельный флаг (`use-client-ip-header`) включают **только** в dev/stage, в prod выключают.

Итог: **IP из заголовка — не истина**, а лишь подсказка от инфраструктуры; без доверенного края сеть «по заголовку» легко обмануть.

## 7. API (кратко)

- **`POST /api/auth/login`** — тело `{"username","password"}`, ответ: `accessToken`, `effectiveRoles`, `privileges`, `expiresInMs`.
- Остальные защищённые ручки — заголовок **`Authorization: Bearer <token>`**.
- **`/api/admin/network-policies`** — GET/POST/PUT/DELETE (админ по привилегии `ORDER_UPDATE_ALL`).

## 8. Как быстро проверить сценарии ТЗ

Пользователь **`netdemo`**, пароль **`password`**, роли: `USER`, `PICKUP_POINT_ADMIN`, `ADMIN`.

```bash
# Только USER (победила политика с /24)
MOCK_CLIENT_IP=173.0.0.5 curl -sS -X POST "$OZON/api/auth/login" \
  -H "Content-Type: application/json" -H "X-Client-IP: 173.0.0.5" \
  -d '{"username":"netdemo","password":"password"}' | jq .

# USER + PICKUP_POINT_ADMIN (победила /8)
MOCK_CLIENT_IP=173.12.34.56 curl -sS -X POST "$OZON/api/auth/login" ...
```

В ответе смотри поле **`effectiveRoles`**. В логах сервера — строки **`RBAC/CIDR:`**.

Проверка **инвалидации по IP:** залогиниться с одним `X-Client-IP`, затем вызвать `/api/me` **без** заголовка (или с другим IP) с тем же токеном — ожидается **401**.

## 9. Связь с Docker / WildFly

В `docker-compose` для `ozon-service` можно передать `JWT_SECRET`, `CLIENT_IP_HEADER_ENABLE`. Базовый URL приложения при деплое на WildFly может включать контекст (например `/ozon`) — его нужно учитывать в `OZON_URL` и в SpringDoc `servers` в `OpenApiConfiguration`.
